NEW retrieval_relay_backpressure.py
---------------------------------
Uses the original auth/route/opaque-byte HTTP handler. A fixed pool starts
only at serve_forever, after upstream setns when used in that role. New CPU
downstream uses8 backend workers versus retained upstream16. Queue128 and
listen backlog256 cover the finite80-client default topology (and96-client
test). No queued request creates a new thread. Userspace holds at most8 active
+128 queued+1 admission socket. Kernel backlog remains finite as well.

Queue wait is45s, not the unsupported initial5s. Every accepted request shares
an absolute59s budget. The backend timeout is min(50,59-elapsed); request body,
connect and response share the remaining budget. A deadline timer shuts owned
backend sockets to prevent a slow-drip response from renewing per-read timeouts.
Queue-full/queue-expired remain explicit503; backend failure/deadline remains
a real HTTP/transport error. Request/result bytes, status, content-type,
top3, ordering and scores are unchanged. No reduction of scientific context or
retrieval algorithm budget, no alternate corpus/index and no empty-doc fallback.

backpressure-stats.json records bounded queue/active peaks, queue rejects,
remaining backend budget and attempted HTTP statuses, without token/query/
response values. It is written at most once per5s plus final shutdown.
The 59s request bound assumes the unchanged actual client timeout is60s;
changing that scientific/runtime client contract would require matching bounds.
Arbitrarily sustained overload can still fail honestly; no finite queue can
guarantee success beyond the preserved client deadline.
