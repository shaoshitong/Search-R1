# Focused compute/synchronization findings (before GPU measurement)

Main746083 and its runtime are unchanged. This is a separate synthetic benchmark for the independent profile allocation. No real training feature/checkpoint is read and no optimizer/EMA/sampler is advanced.

Current update is32 questions,10 genuine native trajectories per question and4 realG5 direct-head views per question. `joint_mixed_direct_pretrain.direct_update` makes32 serial native/head/backward calls. Native sequence length is293, hidden3584, MLP18944; cached L26 features still require training the full final native block on93760 tokens per optimizer update. This is not a single scalar layer operation.

The head has **two** bidirectional attention layers, dim256,8heads, plus3584→256 projection and token/type embeddings, over374 slots includingCLS. Actual `MixedTokenHead` parameter count from a meta-device construction is2,573,825. The configured native block's expected parameter count from Q/K/V/O,3 MLP matrices, norms and biases is233,057,792 (runtime script reports actualnumel). Its dense linear forward cost perB32 is43.7018TFLOPs; this is analytical GEMM work, not measured hardware throughput. The script records exact loaded parameter counts, a scoped FLOPs model and optional PyTorch-supported-operator FLOPs. Fused FlashAttention counts may be absent; supported operator counts are never called complete totalFLOPs.

Static synchronization sites in each one-question path: native `bool(mask[:,0].all())`; head question-mask/position `torch.equal` twice; full selected hidden `bool(isfinite(clean).all())`; worker finite-loss `bool`; per-loss and prediction `.cpu().tolist()` twice. At update end each parameter is separately finite-checked and its norm converted toPythonfloat, then clipping occurs. These impose host/device barriers and many launches. The full selected hidden finite check touches4×5×293×3584=21,002,240 values per question,672,071,680 perB32. Their actual cost must be separated from feature decode/IO and native GEMM time by measured profiling, not guessed from source.

`native_mixed_compute_benchmark.run(config,output,device)` or CLI `--source-config path --output path` loads only the official block viaProbe and the qualified direct-head factory. It avoids worker.initialize/official_sources and all training-bank hashing. Config uses model_dir,official_inventory,head_seed; optional compute_benchmark={micro_questions:[1,4,8,16,32],warmup:1,repeats:3,synchronization_ablation:true,profile_supported_flops:true}. Each case keeps exactly the same balanced true-G5 objective and source weights, mean32(mean4BCE), with10/40/80/160/320 native rows per call. Gradients are compared with micro1 allowing BF16 batch/reduction differences. OOM is reported without truncation/dtype fallback.

CUDAEvents split native forward, head/gather forward, head/gather backward and native backward through a hidden-gradient boundary hook. Wall time is recorded separately; event stream elapsed includes possible host enqueue starvation and is not a pure kernel utilization counter. Gradient checks/clipping and host metric copies have separate timings. A final micro1 case delays host copies and vectorizes gradient-check reductions without changing gradients or the loss; no active-source monkeypatch occurs. At least one warmup and three timed repeats are required per case. Input generation, source setup, reference-gradient transfer and supported-op profiler overhead are excluded from measured repeats.
